# Database project (PLAT-15)

Status: draft for review.

The schema lives in `database/` as the desired state. There are no migration files: each deploy compares `database/schema/` with the live database using [pgschema](https://github.com/pgplex/pgschema) and applies only the difference.

## Layout

| Folder | Holds |
| --- | --- |
| `schema/` | The desired schema, one file per table, view, function, trigger or policy, grouped by domain. `schema/main.sql` includes them in dependency order. |
| `pre-deploy/` | Scripts that must run before a schema change, such as copying data before a column rename. Each runs once and is recorded. |
| `post-deploy/` | Re-runnable reference data written as upserts: countries, statutory rule packs, error codes, plans, roles. |
| `tests/` | Tenancy and row-level security tests run against a fresh database in CI. |

## Workflow

1. Edit the files in `schema/`.
2. Run the plan against your local database and read the generated change script.
3. Run `scripts/check.sh` (it applies the schema to a fresh database and runs the tests), then open a pull request with the plan in its description. CI takes this over once it's switched on after MVP 1.
4. On merge, staging gets the change. Production gets the same reviewed plan after approval.

## Conventions

Follow the conventions and review checklist on the Schema Design page. In short:

- snake_case, plural table names; `uuid` primary keys generated by the app (version 7)
- `organization_id not null` on every customer table, `company_id not null` on company-owned tables, composite foreign keys that include `organization_id`
- row-level security enabled on every customer table, in the same file as the table
- money as `numeric(18,2)` with a `currency char(3)`
- status values as `text` with a `check` constraint, not enums
- effective-dated rows use `valid_during daterange` with an exclusion constraint
