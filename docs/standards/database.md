# Database project (PLAT-15)

The schema lives in `database/` as the desired state. There are no migration files: each deploy compares `database/schema/` with the live database using [pgschema](https://github.com/pgplex/pgschema) (v1.13.1, Apache-2.0) and applies only the difference.

Target: PostgreSQL 18, the version we run locally, in tests and on DigitalOcean Managed PostgreSQL.

## Layout

| Path | Holds |
| --- | --- |
| `schema/main.sql` | Includes every schema file in dependency order (`\i`) |
| `schema/<domain>/` | One file per table, function or view, with its row-level security policies and grants in the same file |
| `pre-deploy/NNNN_name.sql` | Scripts that run once, before the schema is applied: roles, copying data before a rename. Recorded in `deploy_scripts` |
| `post-deploy/NNNN_name.sql` | Re-runnable scripts that run after every deploy: reference data as upserts (countries, rule packs, error codes, plans, roles) |
| `tests/` | SQL tests and `run.sh`, which tests the whole project in Docker |
| `db.sh` | `plan` and `deploy` commands |
| `Dockerfile` | The tools image: PostgreSQL 18 client plus pgschema |

## Commands

```bash
docker compose up -d --build               # local database: deploys automatically on every start
docker compose run --rm db-tools plan      # local database: show what a change would do, without applying it
database/tests/run.sh                      # fresh database: deploy, re-plan (must be empty), redeploy, tests
```

For staging or production, run the same image with that database's `PGHOST`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` and `PGSSLMODE=require`.

## Workflow

1. Edit the files in `schema/` (and add a `pre-deploy/` script if data must move first).
2. Run `docker compose run --rm db-tools plan` and read the change script.
3. Run `scripts/check.sh`, then open a pull request with the plan in its description.
4. After merge, deploy to staging; production gets the same plan after approval.

## Rules learned while setting this up

- **Grants are part of the schema.** pgschema manages privileges, so `grant … to pesaroll_app` goes in the table's schema file. A grant made anywhere else is seen as drift and revoked on the next deploy.
- **Roles are not part of the schema.** pgschema doesn't create roles; `pre-deploy/0001_roles.sql` does.
- **No built-in temporary database.** pgschema normally validates plans in a temporary PostgreSQL it downloads at runtime. `db.sh` points it at a scratch database on the same server instead (`<database>_plan`, created on first use), so deploys never depend on a download.
- **Not as root.** The tools image runs as the `postgres` user.
- **A second plan must be empty.** `tests/run.sh` fails if a plan right after a deploy shows any change; that's how we catch schema files that don't round-trip.
- **Reference data that a new foreign key points to must exist first.** Post-deploy scripts run after the schema is applied, so on a database that already has rows, a new foreign key to a freshly created reference table would fail. In that case add a pre-deploy script that creates and fills the reference table first (with the same definition as its schema file).
- **Renames need a pre-deploy script.** pgschema sees a renamed column as a drop and an add; copy the data in a pre-deploy script first.

## Conventions

Follow the conventions and review checklist on the Schema Design page. In short:

- snake_case, plural table names; `uuid` primary keys, version 7 (generated by the app with `Guid.CreateVersion7()`)
- `organization_id not null` on every customer table, `company_id not null` on company-owned tables, composite foreign keys that include `organization_id`
- row-level security enabled on every customer table, in the same file as the table
- money as `numeric(18,2)` with a `currency char(3)`
- status values as `text` with a `check` constraint, not enums
- effective-dated rows use `valid_during daterange` with an exclusion constraint
